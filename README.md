## 1. What is Brand Compass?

Brand Compass is an **AI-powered SaaS brand intelligence platform**. A user enters a brand name, website URL and social media handles — the platform generates a comprehensive diagnostic report covering:

- **Brand positioning analysis** — how the brand is perceived, its archetype, voice and value proposition
- **SWOT analysis** — strengths, weaknesses, opportunities and threats
- **Competitive landscape** — who the real competitors are, their messaging angles, their market position
- **SEO scoring** — how well the brand ranks on search engines (via SerpAPI real SERP data)
- **GEO scoring** — whether the brand is cited by AI systems (ChatGPT, Claude, Perplexity) and how favorably
- **Meta Ads intelligence** — what paid ads the brand or its competitors are currently running (Radar+ tier)
- **Actionable recommendations** — quick wins and strategic improvements generated by Claude

### Who it's for

- Marketing directors and brand managers (Mid-market / SME)
- Digital agencies managing multiple client brands
- E-commerce founders tracking their brand presence

## 2. Architecture Decision Log

This section documents every significant choice and why it was made, combining the best decisions from two architecture reviews.

### Decisions taken from the second architecture (new)

| Decision | Rationale |
|---|---|
| **Firecrawl for website extraction** | Converts any URL into clean, AI-friendly markdown in one API call. Eliminates the need to build a custom website scraper — a significant time saving for MVP. |
| **ARQ as the async task queue** | Lightweight Redis-native async queue for Python. Better than raw FastAPI `BackgroundTasks` for real workloads — supports retries, worker processes and job visibility. Simpler than BullMQ. |
| **Credit-based pricing (not unlimited)** | Explorer / Growth / Agency tiers with monthly credits. More predictable margins than unlimited queries — each report consumes a credit, costs are capped per user. |
| **Brand-level cache (24h TTL)** | If two users request the same brand within 24 hours, the second request reuses cached research. Directly reduces Claude, SerpAPI and Apify costs. |
| **Single Railway deployment** | Frontend, backend, worker, PostgreSQL and Redis all on Railway. Zero cross-provider configuration complexity for MVP. |
| **OpenTelemetry for observability** | Request latency, AI provider latency, DB and queue performance tracked from day one. Prevents cost surprises at scale. |

### Decisions kept from the first architecture review (v2)

| Decision | Rationale |
|---|---|
| **Clerk for auth** | Handles JWT, social login and session management out of the box. Zero backend auth code. The new README had no auth solution specified — this fills the gap. |
| **Lovable for landing page** | The new README says "Next.js frontend" for everything. Landing page and pricing page in Lovable saves 1.5–2 days at MVP budget. Report viewer and dashboard stay custom. |
| **SerpAPI for SEO** | The new README's SEO engine only parses meta tags and headings. SerpAPI gives actual Google SERP data — real rankings, featured snippets, knowledge panels. Much stronger product. |
| **Perplexity for competitive intel** | Real-time web-aware research that Claude alone cannot do. Kept as a data provider alongside Claude. |
| **Apify for Meta Ads (Radar+)** | Only viable path to competitor ad data. Kept with explicit risk flagging and Day 0 test requirement. |
| **GEO scoring via AI probing** | The new README described GEO scoring vaguely as "knowledge graph signals". The v2 methodology (probe Claude + Perplexity with test queries, parse responses, score visibility + sentiment + consistency) is concrete and buildable. |
| **Ora Telecom infrastructure reuse** | DNS, email relay, base hosting — not mentioned in either original README. Direct cost reduction. |
| **Risk register** | Apify risk, GEO methodology risk and budget reality check — essential context for project decision-making. |

### Decisions deliberately removed

| Removed | Why |
|---|---|
| Terraform IaC | Zero benefit at this scale. Railway config handles infrastructure. |
| PostHog | Nice-to-have analytics deferred to V2. Saves integration time and one more third-party dependency. |
| BullMQ | ARQ is the right Python-native queue. BullMQ is Node.js. |
| Upstash Redis free tier | 10k operations/day cap hits real limits quickly. Railway managed Redis is persistent and uncapped. |

> **Note — OpenAI reinstated:** OpenAI/ChatGPT was previously removed from GEO scoring due to the absence of a free API tier. The client devis explicitly requires *"test de visibilité dans ChatGPT, Claude et Perplexity"* — so OpenAI is back in the stack. Cost impact is minimal (~€0.02 per report using gpt-4o-mini).

## 3. Subscription Model

Credits-based model. Each brand analysis consumes one credit. Credits expire monthly.

| Feature | Explorer | Growth | Agency |
|---|---|---|---|
| Monthly credits | 25 | 100 | 500 |
| Price | €49/mo | €149/mo | €399/mo |
| SEO scoring | ✅ | ✅ | ✅ |
| GEO scoring | ✅ | ✅ | ✅ |
| SWOT + positioning | ✅ | ✅ | ✅ |
| Competitive analysis | ✅ | ✅ | ✅ |
| Report history | ✅ | ✅ | ✅ |
| Meta Ads intelligence | — | ✅ | ✅ |
| Competitive alerts | — | ✅ | ✅ |
| Weekly automated report email | — | — | ✅ |
| Priority support | — | — | ✅ |

**Premium block strategy:** Meta Ads and alert sections are visible but blurred for Explorer tier users, with an upgrade CTA. The backend gates the actual data server-side via subscription guard middleware — the blur is only a UX layer.

**Credit economics:**
- Cost per Explorer report: ~€0.20–0.35 (Claude + SerpAPI + Firecrawl, no Apify)
- Cost per Growth report (with Meta Ads): ~€2.20–5.30 (adds Apify run)
- Explorer margin at €49: healthy if average user runs fewer than ~140 reports/mo (effectively impossible at 25 credit cap)

### Architecture principles

1. **Cache first** — before calling any paid API, check the 24h brand cache. If another user analyzed the same brand today, reuse the result.
2. **Credits deducted before queuing** — the credit is consumed when the job is created, not when it completes. Prevents users gaming retries.
3. **Graceful degradation** — if Apify fails, the report delivers without the Meta Ads section and flags it as "unavailable". No hard failures.
4. **Single Railway deployment** — all services (Next.js, FastAPI, ARQ worker, PostgreSQL, Redis) run on Railway. Zero cross-provider configuration at MVP.
5. **Prompt-as-configuration** — all Claude prompts live in version-controlled YAML files. The partner can tune them without touching code.
6. **Cost-aware from day one** — every API call writes to `report_costs`. Cost per report and cost per user are visible in real time.

### 6.3 ARQ Task Queue

ARQ is a lightweight async task queue for Python, backed by Redis. It replaces both raw FastAPI `BackgroundTasks` (no retry support) and BullMQ (Node.js only).

```python
# How a report job is created
async def create_report(brand_input: BrandInput, user: User):
    await deduct_credit(user)                    # Credit consumed before queue
    job = await redis.enqueue_job(
        "generate_report",
        brand_input=brand_input,
        user_id=user.id,
        report_id=new_report_id,
    )
    return {"job_id": job.job_id}

# ARQ worker picks it up
async def generate_report(ctx, brand_input, user_id, report_id):
    await orchestrator.run(brand_input, user_id, report_id)
```

The frontend opens `GET /sse/reports/{report_id}` to stream live progress while ARQ processes the job in the background.

### 6.4 Website Fetcher (Firecrawl)

Firecrawl converts any URL into clean, structured markdown — removing navigation, ads, footers and irrelevant content. This is what gets fed to Claude for analysis.

Without Firecrawl, building a reliable website scraper is 2–3 days of work. With Firecrawl, it's one API call.

### 6.5 SEO Scoring Engine

**Data source:** SerpAPI (real Google results — not meta tag parsing)

```
Scoring formula (0–100):

Brand SERP ownership       (0–30 pts)
  Brand domain is #1:       20 pts
  Featured snippet owned:    7 pts
  Knowledge panel present:   3 pts

Keyword ranking average    (0–40 pts)
  Extract top keywords from homepage via Firecrawl output
  Query SerpAPI for each → record domain rank
  Weighted average position → points

SERP feature presence      (0–20 pts)
  People Also Ask count:    up to 10 pts
  Related searches:         up to 10 pts

Negative content penalty   (0–10 pts, inverted)
  Deduct per negative result on page 1
```

### 6.6 GEO Scoring Engine ⚠ R&D

**Data sources:** Claude API + Perplexity API + OpenAI API

> **Why three engines:** The client devis explicitly requires visibility testing in ChatGPT, Claude and Perplexity. These are the three dominant AI assistants users actually consult — each has a different training data mix and knowledge cut-off, so a brand can be visible in one and invisible in another.

GEO (Generative Engine Optimization) measures how visible a brand is inside AI responses. There is no established industry methodology — this is invented and validated as part of the project.

```
GEO Score = Visibility (40%) + Sentiment (40%) + Consistency (20%)

Visibility (0–40 pts) — per engine (Claude, Perplexity, ChatGPT):
  Probe queries:
    "What do you know about {brand_name}?"
    "What are the best {industry} brands?"
    "Compare {brand_name} vs {competitor_1}"
  Score per engine:
    Full mention with details:   ~13 pts  (40 pts ÷ 3 engines)
    Partial / indirect mention:   ~7 pts
    Not mentioned:                 0 pts

Sentiment (0–40 pts) — for each engine that mentions the brand:
  Probe queries:
    "What are the pros and cons of {brand_name}?"
    "Would you recommend {brand_name}?"
  Score per engine:
    Positive:   ~13 pts
    Neutral:     ~7 pts
    Negative:     0 pts

Consistency (0–20 pts):
  Compare brand description across all three engines
  High overlap (2+ engines agree):   20 pts
  Medium overlap (1 engine differs): 10 pts
  Contradictory:                      0 pts

Final GEO score: 0–100 (labeled "Beta" in UI)
```

**Models used:**
- Claude: `claude-sonnet-4-5` (already in stack)
- Perplexity: `sonar` (already in stack)
- OpenAI: `gpt-4o-mini` (cheapest capable model, ~$0.15/1M input tokens)

**Cost per GEO analysis (3 engines × ~2 probes each):**

| Engine | Calls | Est. cost |
|---|---|---|
| Claude | 2 | ~€0.03 |
| Perplexity | 2 | ~€0.02 |
| OpenAI gpt-4o-mini | 2 | ~€0.02 |
| **Total GEO** | 6 | **~€0.07** |

**R&D tasks (time-box: 3 days max):**
- Test methodology on 10 brands (global known brands + small local brands)
- Validate that scores correlate with expected brand awareness levels
- Compare results across all three engines — identify systematic differences
- Define "sentiment" parsing logic for free-form AI text
- Document methodology publicly (builds user trust)
- Fallback if unstable: binary visibility check only (mentioned / not mentioned per engine)

### 6.7 Meta Ads Integration (Apify) — Growth+ only

```

1. User requests Growth+ report
```

## 10. Caching Strategy

Every expensive external API call is cached at the brand level for 24 hours.

```
Cache key: SHA256(brand_name.lower() + website_url)

Cached per provider:
  firecrawl   → website content (markdown)
  serpapi     → SERP results for brand queries
  claude      → positioning, SWOT, competitive analysis outputs
  perplexity  → competitive intelligence outputs
  apify       → Meta Ads library results (Growth+)

On new report request:
  1. Check cache for each provider
  2. Use cached result if exists and not expired
  3. Only call provider API for what's missing
  4. Write new results to cache

Result: if two users analyze the same brand on the same day,
        the second report costs ~€0 in provider fees.
```

**Cache TTL:** 24 hours. Configurable per provider in `config.py`.

## 11. Cost Control

Every provider call writes a row to `report_costs`:

```sql
INSERT INTO report_costs (report_id, provider, tokens_in, tokens_out, cost_cents, duration_ms)
VALUES ($1, 'claude', 1200, 800, 3, 2100);
```

This enables real-time visibility into:
- Cost per report (by tier)
- Cost per user (to identify unprofitable accounts)
- Provider efficiency (latency vs cost tradeoff)
- Monthly cost forecasting
